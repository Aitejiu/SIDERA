# 使用 SIDERA

SIDERA 按“任务 → 子任务 → WorkerItem”组织工作。先看任务是否按预期推进，
需要判断某一块的细节时再深入，不必从所有 Agent 的完整日志开始阅读。

尚未启动的用户请先完成[快速开始](../deployment/initial-demo.md)。
下文先介绍新版真实执行。无模型 Demo 和 legacy 运行栈是独立入口，见文末说明。

## 先配置智能体

1. 在 `/workspaces/{workspace_id}/agents` 打开“本地会话”，用 CLI 签发的令牌连接。
2. 进入“运行环境”，发现或指定本机 OpenCode 的绝对可执行路径，检查实际版本后登记。
3. 返回“新建 Profile”，选择 Runtime、模型、并发和指令，保存可复用配置。
4. 在“默认安排”选择主 Agent、Planner 和 Worker。一个 Profile 可以同时担任多个角色，
   用户仍可在具体规划中修改负责人。首次运行任务还要完成[项目配置](../deployment/initial-demo.md#配置项目与验证)。

Runtime 是主机上的 Harness，Profile 是配置，不是永远运行的进程。实际开始工作时
才创建 Run。保存新的 Profile 修订或默认安排不会改写已有任务的执行版本和上下文。
Profile 的“概览、工作、能力、设置”用于查看历史与配置；“使用此 Profile 聊天”可打开对话。

### 首次配置建议

在“运行环境”中选择发现到的 OpenCode，或填写本机 `command -v opencode` 返回的绝对路径。
同一 Runtime 的容量由所有 Profile 共享；主对话也占用 Run 和会话容量。
体验聊天、规划和少量并行 Worker 时，可将“活跃 Run 上限”设为 `4`、“原生会话上限”
设为 `8`。这是小任务的配置示例，不是固定要求；更高并发可能增加模型费用。

先建三个 Profile，方便分别调整指令与权限，也可以只建一个供多个角色复用：

| 安排 | 示例名称 | `Native coding tools` | 并行安排上限示例 |
| --- | --- | --- | --- |
| Main | 需求助手 | `none` | 1 |
| Planner | 任务规划者 | `none` | 1 |
| Worker | 编码执行者 | `write` | 2 |

每个 Profile 都需选择 Runtime、明确的模型路由和授权凭据，并保持启用。
在指令中描述它要做的工作；Main 用于澄清目标和调用任务工具，Planner 用于提出依赖与分工，
Worker 用于完成局部任务并给出结果。名称和指令不会自动授予额外权限。
若三种角色复用同一 Profile，要同时考虑其并行上限，避免主对话占满容量后规划无法启动。

`Native coding tools` 默认为 `none`，不会因为任命为 Worker 自动开启。
需要改代码时明确选择 `write`；它同时允许原生编辑和命令执行，只应授予可信项目。
`read` 仅开放受支持的读取工具。权限还受任务工作空间的授权限制，这不是操作系统沙箱。

保存后，在 Profile 页标题处可以找到它的 UUID 和 `R1` 等修订号，供首次
[CLI 项目配置](../deployment/initial-demo.md#配置项目与验证)使用。保存修订后以实际版本为准，
不要把文档中的占位 UUID 当成已创建的 Profile。

在“能力”配置指令及受支持的 Skills、MCP、集成资源引用。以当前 Runtime 报告为准：
“支持未确认”不等于可用；不支持的思考设置或集成不会因保存 Profile 而变成可执行能力。
资源引用保留版本，不会悄悄使用另一份最新内容。

## 模型与凭据

模型填写明确的 `provider/model` 路由，例如 `opencode-go/deepseek-v4.1-flash`，
前提是你的账户和本机 OpenCode 支持它。选定模型与实际观察到的回复模型分别显示；
“模型未观察到”不代表零消耗或成功，也没有自动 fallback。

macOS 凭据界面需要先安装可选 Keychain 依赖并显式启用托管存储，见
[凭据设置](../deployment/initial-demo.md#配置模型凭据)。启用后，在 Profile 设置展开
“配置凭据引用”，选择或“新建凭据”，为 OpenCode Go 将注入目标设为 `OPENCODE_API_KEY`，
点击“绑定凭据”并“保存 Profile”。Provider credential environment 只填写变量名，不填 key。

新版 OpenCode 使用每次 Run 独立的 HOME/XDG 配置，只读取明确授权的凭据引用，
不会复制全局 OpenCode 登录，也不会因为终端里存在 DeepSeek key 就自动使用它。
不要把 key 放进指令、资源正文或聊天。

## 从需求到确认

进入聊天，选择主 Agent Profile 并提供目标、约束和验收标准。主 Agent 可以提交规划，
Planner 产出候选方案；聊天回复本身不代表任务已经创建或执行。
查看关联的规划状态与方案，检查子任务、依赖、WorkerItem 和各自负责人，再确认当前版本。
人类负责人目前指本机当前用户，不表示已经支持邀请其他团队成员。
执行需要 Profile 负责人和相应运行环境可用。

## 试一个有依赖的小任务

先完成安装、角色默认值和项目配置。选择一个允许试验、已提交 HEAD 且测试可运行的
Python Git 项目；下面的示例不是自动导入的样例数据，会调用你配置的模型：

```text
为当前 Python 项目增加一个 JSON 格式校验 CLI。
先确定参数、退出码与错误输出格式；接口确定后，实现 CLI 和编写测试可并行；
最后集成并运行项目测试。无效 JSON 应返回非零退出码，不新增联网依赖。
只处理当前项目。先给我规划、依赖和各部分负责人，等我确认再执行。
```

在聊天中查看关联规划，而不是只阅读回复正文。核对目标、前后依赖、WorkerItem 和
负责人；需要由 Agent 执行的项选择已启用的编码 Profile。确认当前规划版本后，
进入任务页看进度，切换 DAG 查看“接口 → 实现与测试 → 集成”的关系。
实际拆分由 Planner 提议、用户确认，不保证每次模型输出完全相同。

需要局部修改时，在有活动会话的 WorkerItem 输入要求，例如“无效输入的错误信息只写入
stderr”。发送后检查投递状态；会话已结束则输入不可用，不要反复点击或期待自动续作。
最后检查成果候选与项目验证结果，再显式验收。

## 查看整体进展

从侧边栏进入任务列表，打开自己的任务。根任务页用于查看整体目标、
各子任务的进度，以及需要你处理的事项。

遇到“需要我”的事项，先查看它属于哪个任务、哪个子任务，再点击进入对应位置。
关联了 WorkerItem 的事项可以直达它的工作空间；任务级事项则在相应任务层级处理。

打开另一个任务会使用独立标签。你可以在任务之间切换，关闭当前标签后回到仍打开的页面。

## 查看子任务与依赖

进入子任务后，重点是这一块由谁负责、各 WorkerItem 走到了哪一步。

- 看板适合日常查看执行、等待和完成状态。
- DAG 适合判断哪些工作可以并行、哪些必须等待前置工作完成。

选择 Worker 后可以先看速览；需要查看完整记录或输入要求，再打开它的 WorkerItem 标签。
WorkerItem 是工作空间，具体执行的 Agent 与会话信息在其中查看。

## 进入 WorkerItem

工作空间中央呈现步骤与持续工作记录，也保留你之前发送的介入消息。
右侧用于查看当前任务、执行 Agent、状态、上下文和可用的用量信息。

可以先看当前步骤和最近记录，再决定是否展开更早的内容。用量缺失表示暂时没有
可用数据，不等于零消耗；没有正文的成果也不应当作已经取得的交付文件。

## 补充要求或纠正方向

在 WorkerItem 底部输入区填写这块工作的新要求，发送前确认当前打开的是目标工作空间。
发送前读取并明确查看最新执行上下文。发送后区分“已受理”“已投递”和“已执行”，
已保存或排队不等于 Agent 已处理完成。

单个 Worker 的介入用于调整当前局部工作。如果要改变整个任务的目标或多个子任务的分工，
应回到主 Agent 讨论并确认新方案，不要把全局变更只发给某一个 Worker。

当输入区不可用时，先查看原因，例如当前没有活动会话、状态正在同步或执行已结束。
如果提示执行上下文发生变化，保留草稿，重新查看当前执行信息后再决定是否发送。

介入只发给当前活动且已接入的 Session。Session 关闭后不会自动新建续作会话。
如果发送结果未知，先查询原操作，不要重复发送或将旧消息自动改绑到新会话。

## 调整负责人和整体需求

尚未执行时，在规划/负责人入口修改安排。执行中的 Profile 交接需要先准备、查看并确认
目标 Profile 和上下文；控制面等待原 Agent 确认停止后再推进目标执行。
WorkerItem 历史保留在同一任务代中，切换负责人不是删除旧会话或重建任务。
交接显示等待或未知时，查询原操作；不要凭页面超时再确认一次。

整体目标或依赖结构改变时，回到主 Agent 提出需求变更并查看新规划。
局部对话不自动更换整个计划。

## 验证与验收成果

执行完成后查看成果候选、变更和项目验证结果，再由用户显式验收。
Agent 自报进度不是通过验证；候选通过检查也不等于用户已接受。
接受结果不会静默修改你原仓库的工作树或分支，应用成果需要另行核对。

## 停止与恢复

结束使用时，先正常停止活动对话，再停止产品服务。关闭过程可能需要等待原操作和
子进程确认退出；`shutdown_pending` 或未知清理状态不能当作已经完成。
使用同一组数据库、目录和稳定身份重启可保留历史，不要为恢复而重新 seed 或 reset。

## Legacy 演示与维护

无模型预置 Demo 和 Interview Demo 只模拟 Agent 输出，不会调用 Provider。
可以用旧 run 的 manifest 执行 Demo 的 `status` 和 `doctor`，见
[本地维护现状](../deployment/initial-demo.md#本地维护现状)。Demo manifest 不会自动变成
维护 inventory；需要备份时，先准备显式清单并停止所有 writer，再使用维护入口的
`doctor`、`backup`、`inspect-backup`、`restore-preflight` 和 `restore`。恢复目标是新的
空目录和新数据库，恢复后的服务默认按只读模式装配，凭据和 Keychain 不在备份范围内。
不要把样例数据库当成日常任务库，也不要在没有确认 source/target 身份的情况下恢复。

## 查看 Agent Trace

从 WorkerItem 打开 Agent Trace。日常进展仍以工作空间中的步骤和工作记录为主，
Trace 用于进一步核对工具调用、消息或错误等具体事件。

先浏览事件列表，按需要筛选类型，再点开事件查看详情。较早的记录按页加载；
未提供的输入输出会保持缺失状态，不会补造内容。

Trace 可能含有代码、路径、工具输入输出和私人信息。对外反馈问题时只提供必要的脱敏片段，
不要直接上传完整会话或凭据。

## 聊天、信箱与知识

聊天用于与已配置的主 Agent 沟通，信箱集中查看通知。Knowledge 是独立的可选服务，
不是新版默认安装后自动可用的知识库；需要另行配置服务、授权与资料。
只运行无模型 Demo 时，聊天不可用、信箱为空并不代表任务看板故障。

当前新版以桌面、本机单人和 OpenCode 为范围。团队分享/RBAC、其他 Harness、
手机和平板，以及更完整的记忆和知识复用仍是后续工作。

需要接入真实 Agent 或自己的工具时，参见[集成与 API](../api/README.md)。
